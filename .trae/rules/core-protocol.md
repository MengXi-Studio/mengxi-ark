## 1. 核心原则

### 1.1 辩证执行

不要盲从。如果我的指令有明显的逻辑漏洞或技术风险，必须提出异议（除非我明确要求"强制执行"）。
特别地：任何让**下层包 import 上层包**（如 utils 引 hooks、biz-components 直接 import runtime）的指令，均违反本项目单向依赖架构，必须拒绝并提出替代方案。

### 1.2 命令与 API 禁止幻觉构造

当涉及到不熟悉的 CLI（如 turborepo、changesets）或包 API 时，禁止凭记忆构造命令。

1. **动作**：先查 `package.json` scripts、官方文档或已有脚本确认真实命令。
2. **验证**：执行前确认命令存在于工程配置中，禁止编造 npm scripts。

## 2. 工作模式

### 交互模式 (默认)

- 遇到技术选型、重大架构变更、新增包或存在多方案时，使用 `AskUserQuestion` 询问。
- 拒绝过度设计，保持方案简单直接；扩展优先（回调/适配器/插槽/钩子），fork 兜底。

### 无人值守模式

- **触发词**： "进入无人值守模式"
- **行为**：
  - 自动选择最佳实践，不再询问。
  - 自动执行 `修改 -> 构建 -> 测试 -> 验证 -> 修复` 循环。
  - **熔断机制**： 若针对同一错误的自动修复尝试超过 **3次** 仍未达到 DoD，**必须立即停止**，退出无人值守模式，并输出"卡点分析报告"等待人工介入。

### 谋定而后动

- **触发词**： "谋定而后动"、"先讨论"
- **行为**： 禁止立即写代码。
- **输出**： 必须先分析需求，并输出一份 **[行动计划清单]**。待用户确认清单后，再逐项执行。

## 3. 完成标准 (Definition of Done - DoD)

任务是否完成，**完全取决于构建、测试与运行时表现**，而非代码静态检查。

**DoD 检查清单（必须全部勾选方可回复"已完成"）:**

- [ ] 代码已保存且类型检查通过（`tsc --noEmit` / IDE 无报错）。
- [ ] **构建通过**：受影响的包 `turbo build` 成功（ES Module 产物 + `.d.ts` 类型声明完整）。
- [ ] **单元测试通过**：新增/修改的纯函数与 hooks 必须有 Vitest 用例且全部通过。
- [ ] **功能已实际运行验证**：在 demo-light（或 demo-platform，涉及 runtime 时）实际跑通关键路径，无控制台报错。
- [ ] **依赖边界无违规**：未新增任何反向/循环 import（下层包不得 import 上层包）。
- [ ] **现场已清理**：移除仅用于调试的临时 `console.log`、注释掉的死代码或断点（保留必要业务日志）。
- [ ] 文档同步：新增/变更的导出 API 已在 JSDoc 标注；涉及用法变化的已更新 VitePress 文档。

## 4. AI 行为规范

### ❌ 严禁行为

1. **占位实现**： 禁止 `return true` 等蒙混过关，必须调用真实实现。如果确实受阻，必须征得同意后创建"技术债清单"。
2. **盲目自信**： 禁止在未运行构建/测试的情况下声称"修复完成"。
3. **过度工程**： 禁止添加未要求的注释、未要求的功能扩展；禁止为一个需求预先抽象。
4. **破坏分层**： 禁止在底层包（utils/theme/hooks）写业务硬编码、业务字典、业务接口地址；禁止 biz-components 硬编码 import runtime（只能 inject 探测）。
5. **绕过适配器**： 禁止在 hooks/components 中直接耦合单一 UI 库 API，UI 差异必须收敛到 UI 适配层。

### ✅ 强制流程

1. **读取**： 修改前必须先读取文件。
2. **修改**： 只做最小必要修改。
3. **验证**：
   - **编译器日志**： 类型检查 + 包构建无报错。
   - **测试日志**： Vitest 输出全部通过。
   - **运行验证**： demo 工程实际运行关键路径。
